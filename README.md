# ros2-dataset-gate

Turns ROS 2 drive logs (rosbag2, sqlite3 or MCAP) into dataset versions that a health report admits or refuses, and that training reads only once admitted, recording the exact version it read. In CI, two workers are killed after writing their outputs and before their receipt: the incomplete version is refused, the resume recomputes those two segments only, and the result is the same dataset as an uninterrupted rebuild in a fresh bucket. All logs are synthetic and generated by the CI; no AWS resource or paid API is needed.

## Run it

```sh
make setup            # uv sync --frozen --all-extras (Python 3.12, uv)
make test             # unit, contract and story tests
make demo             # needs Docker with compose, for the SageMaker local container
make demo-no-docker   # same story, training run as a local process
make terraform-test   # needs Terraform >= 1.11
```

On macOS the segment ids of `.db3` bags differ from the CI's (the bytes depend on the installed SQLite), so child indices and the split-by-segment example differ; the dataset version ids are the same. That is the separation of source integrity and dataset identity at work.

<summary>How it works</summary>

### Time

`header.stamp` is the acquisition time of `Image` and `PointCloud2`; `log_time` is the recording (receive) timestamp the recorder put on the message. Pairing uses `header.stamp`: each point cloud is paired with the nearest camera frame within 25 ms, and the statistic is a nearest-pair timestamp residual. It is read modulo the camera period: within half a period (25 ms at 20 Hz) it is the offset between the two stamp series; beyond, it folds over: an offset of 30 ms reads -20 ms, -40 ms reads +10 ms (under the 10 ms threshold, so retained), 50 ms reads 0. Telling those apart needs trigger or synchronisation metadata, which these bags do not carry. The difference of `log_time - header.stamp` between camera and lidar is reported as an observed offset; it mixes transport and clock differences. When the header clocks do not share a reference with the recording clock, the verdict is `clock_not_comparable`: residuals are not evaluable.

### Streams

The observation window of a segment is from its first to its last `log_time`. A required topic with no message is `required_stream_absent` ("dead sensor" would be a guess: a recording filter or a partial transfer give the same picture); with fewer than 2 messages it is `stream_insufficient`. Every silence above `max_gap_s` is its own `stream_gap`, including at the start or the end of the window. `low_rate` is the rate while the stream is active, gaps left out. `low_pairing` fires when too few point clouds have a camera frame within the pairing window. Frozen content (identical pixels on consecutive frames) and degraded LiDAR (share of finite points) are separate findings. Each carries segment, topic, interval, measure, threshold and action.

### Re-uploads and duplicates

A sample is one point cloud and its paired camera frame. The observation key is (capture id, point-cloud acquisition stamp). Candidates with that key are grouped into variants by camera stamp, camera content, point-cloud content and label; each variant is one observation, kept once, preferring the segment the previous version already published, then the earliest segment. Two variants for one key are a possible duplicate: both kept, both reported. Identical pixels in another capture or at another instant are distinct observations. A byte-identical upload collapses at submission.

### Train and validation

Assignment is by capture: the previous version's registry wins, new captures are placed by a salted hash (`split-4`, picked so that the 6 demo captures land on both sides). A capture with samples on both sides is a leakage group; one is enough to refuse admission. The demo builds a misconfigured variant (`split.unit = segment`) to show the gate firing.

### Capture identity

The uploader declares the capture and vehicle of each bag (an upload manifest); rosbag2 `custom_data` is only a fallback, because Humble metadata does not have it. In the demo, the tractor-04 bags have no `custom_data` and are identified by declaration. A bag with neither is quarantined as `capture_identity_missing`. Nothing is derived from file names.

### Damaged bags

A bag that cannot be read (missing or invalid `metadata.yaml`, truncated MCAP, malformed `.db3`, one truncated message, divergent message definition, unsupported layout) is quarantined: the original stays with its object version, the receipt records the reason, the worker exits 0 and the batch continues. A truncated MCAP is quarantined and recovery (`mcap recover`) is not attempted.

### Identities, stored apart

| Object | Key | Covers |
| --- | --- | --- |
| Source integrity | submission | SHA-256 and S3 object version of every raw file, checked by the worker before reading |
| Computation | `receipts/<segment>/cmp-...` | segment source digest, annotations of its capture, analysis parameters, worker code, lockfile and image; change one and the segment is recomputed |
| Dataset content | `datasets/<version_id>.json` | published samples (capture, stamps, content hashes, label, split), schemas, calibration digests |
| Build and admission | `builds/<build_id>.json` | submission, full recipe, receipts used, worker and publisher provenance, gates and verdict |
| Layout | `layouts/<layout_id>.json` | which shard row holds each sample |

The same content republished under another name or another admission policy reuses the same `datasets/` object and gets a new build: no conflict, nothing overwritten. Canonical encodings are in `src/dsgate/canon.py`. The git commit is metadata only; editing this README changes no digest.

### Batch protocol

1. The submission freezes every input: key, object version, size, SHA-256, declared identity.
2. A plan maps array index `i` to a stable segment id and names the worker provenance it expects. 0 segments: nothing submitted; 1: a plain job, without `arrayProperties` and without `AWS_BATCH_JOB_ARRAY_INDEX`; 2 to 10,000: one array; more: waves.
3. A worker refuses to run if its code, lockfile or image differ from the plan (exit 5). It writes its outputs under content-addressed keys, then its receipt last, each with `If-None-Match: *`. An existing key is compared by SHA-256: identical is reused, different is a conflict (exit 4).
4. A resume lists the segments with no receipt for this exact computation and writes a new, compacted plan; it never re-indexes the original list.
5. A version is built from receipts only. A conditional write does not make a computation happen once; it makes a second contribution impossible.

In `infra/`, the worker role may only `PutObject` with `If-None-Match` (condition `s3:if-none-match`), the job definition takes an image pinned by digest, Spot reclamations (`Host EC2*`) are retried and every exit code stops (`on_exit_code = "*"`), to be resumed from the frozen submission.

### Training

`launch()` is the only entry point: gate, then export, then train. For an incomplete or non-admitted version nothing is exported, no image is built, no container starts. The launcher passes the SHA-256 of the exported manifest; `training/train.py` refuses another digest, re-checks the gates and the capture separation, checks that the content hashes to the requested version id, and verifies every shard and every sample row before a few gradient steps. `model.json` carries the version id and the manifest digest.

## Adaptation points

| What | Where |
| --- | --- |
| Required topics, types, expected rates | `required_topics` in `config/recipe_*.json` (validated: unknown keys and unimplemented values are refused) |
| Which topics are paired | `pairing.reference` (a PointCloud2 topic) and `pairing.match` (an Image topic) |
| Custom message types | `src/dsgate/bagread.py` decoders and `src/dsgate/recipe.py` supported types |
| Capture identity | the `declared` mapping of `batch.upload_bags` (or rosbag2 `custom_data` on recent distributions) |
| Policy and thresholds | `thresholds`, `policy`, `split` and `admission` in the recipe |
| Output for training | `export()` in `src/dsgate/train_launch.py` and the channel contract read by `training/train.py` |

Segments are the bags as uploaded; the pipeline does not re-cut them. The generator cuts its bags on `log_time`.

## Not in this repository

Radar, a web interface, multi-GPU training, a larger infrastructure, Weights & Biases logging, MCAP recovery, real driver layouts beyond the checked subset, and any performance figure: nothing here was measured at fleet volume.
