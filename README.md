# ros2-dataset-gate

Turns ROS 2 drive logs (rosbag2, sqlite3 or MCAP) into explicit dataset versions. An interrupted build cannot corrupt a version, a health report decides whether the version is admitted, and training refuses anything else and records the exact version it read.

All logs here are synthetic and generated by the CI. No AWS resource or paid API is needed for the demonstration.

## How it works

### Time

`header.stamp` is the acquisition time of `Image` and `PointCloud2` messages; `log_time` is when the recorder wrote them. Pairing and skew use `header.stamp` only. `log_time` cuts segments and places intervals on one clock. Two tests pull in opposite directions: a camera that reaches the recorder 60 ms late with aligned acquisitions raises no skew (only an informational `recording_delay`); a camera stamped 18 ms off with aligned arrival is caught. When the two header clocks do not share a reference with the recorder clock, the verdict is `clock_not_comparable`: skew is not evaluable, it is not reported as a huge skew. Close timestamps do not prove that the sensors are physically synchronized.

### Streams

A topic listed in `required_topics` and absent from the bag is `required_stream_absent`, not "dead sensor": a recording filter, a rename or a partial transfer give the same picture. Gaps, low rate (computed over the segment, gaps already reported left out), frozen content (identical pixels on N consecutive frames) and degraded LiDAR (share of finite points on consecutive sweeps) are separate findings. Each finding carries segment, topic, interval, measure, threshold and the action the policy maps it to.

### Re-uploads and duplicates

A sample is one LiDAR sweep and the camera frame within 25 ms of it. Two candidate samples with the same capture id, the same acquisition stamp and the same content are one observation: the re-cut upload in the demo overlaps two existing segments and contributes nothing new. The same capture and stamp with different content is reported as a possible duplicate and both are kept. Identical pixels in another capture or at another instant are distinct observations, and the demo keeps them. A byte-identical upload has the same source digest and collapses at submission.

### Train and validation

Assignment is by capture (`split.unit = capture`): the previous version's registry wins, new captures are placed by a salted hash. A capture with samples on both sides is a leakage group, and one is enough to refuse admission. The demo builds a misconfigured variant (`split.unit = segment`) to show the gate firing.

### Damaged bags

A bag that cannot be opened is quarantined: the original stays where it is with its object version, the receipt records the error, and the rest of the batch continues. The worker exits 0, because a data defect is a result, not a crash. Here a truncated MCAP (no footer) and a truncated `.db3` (`database disk image is malformed`) are both quarantined. `mcap recover` could salvage part of an MCAP; it is not attempted, and doing it would need its own state and a statement of what was lost.

### Three identities

| Identity | Covers | Does not cover |
| --- | --- | --- |
| Source integrity | SHA-256 of every raw file plus its S3 object version, frozen in the submission and checked by the worker before reading | file names |
| Dataset version id | Canonical JSON of the published samples (capture id, acquisition stamps in ns, camera and point-cloud content hashes, label in mm, split), the schemas (type and RIHS01 hash) and the calibration digests | storage format, recipe, code, git commit |
| Build provenance | Recipe digest, digest of this package's own source files, `uv.lock` digest, container image | the git commit, which is kept as metadata only |

Canonical encodings are spelled out in `src/dsgate/canon.py`: integers only in identity-bearing JSON, sorted keys, camera bytes prefixed by encoding and geometry, point clouds as little-endian float32 with every NaN rewritten to one bit pattern. A test writes the same recording as sqlite3 and as MCAP: different raw bytes, same logical content. Editing this README changes none of the digests.

### Batch protocol

1. The submission freezes every input: key, object version, size, SHA-256.
2. A plan maps array index `i` to a stable segment id. 0 segments: nothing is submitted; 1: a plain job, without `arrayProperties` and without `AWS_BATCH_JOB_ARRAY_INDEX`; 2 to 10,000: one array job; more: waves of at most 10,000.
3. Each worker writes its outputs under content-addressed keys, then its receipt last. Every one of these writes is a `PutObject` with `If-None-Match: *`. When the key exists, the existing bytes are compared with the expected bytes by SHA-256, never by ETag: identical is reused, different is a conflict (exit 4).
4. A resume lists the segments without a receipt and writes a new, compacted plan. It never re-indexes the original list, so a sibling finishing meanwhile cannot shift the mapping (a unit test shows the naive version losing segments).
5. A version is built from receipts only. A conditional write does not make a computation happen once; it makes a second contribution impossible.

Exit codes: 0 receipt written (retained, excluded or quarantined); 3 the source bytes differ from the submission; 4 conflict; anything else is a bug or an infrastructure failure. In `infra/`, the job definition retries Spot reclamations (`Host EC2*`) and lets everything else exit, to be resumed from the frozen submission.

### Training gate

`dsgate.train_launch.gate` refuses a version that is incomplete or not admitted before any export, image build or container start. Inside the container, `training/train.py` refuses again unless the manifest hashes to the version id it was asked for, every shard matches its content hash and every sample row matches the hash in the manifest. It then runs a few gradient steps of a tiny linear model on the samples it verified and writes `model.json` with the version id and the SHA-256 of the manifest it read.

## Adaptation points

| What | Where |
| --- | --- |
| Required topics, expected rates | `required_topics` in `config/recipe_*.json` |
| Custom message types | `SUPPORTED` in `src/dsgate/bagread.py`, plus registering the definitions in the `rosbags` typestore |
| Time source and pairing | `time_source` and `pairing` in the recipe, rules in `src/dsgate/checks.py` |
| Capture identity | `capture_identity()` in `src/dsgate/bagread.py` (here: rosbag2 `custom_data`, never file names) |
| Policy and thresholds | `thresholds`, `policy`, `split` and `admission` in the recipe |
| Output for training | `export()` in `src/dsgate/train_launch.py` and the channel contract read by `training/train.py` |

## Run it

```sh
make setup            # uv sync --frozen --all-extras (Python 3.12)
make test             # unit, contract and story tests
make demo             # needs Docker with compose, for the SageMaker local container
make demo-no-docker   # same story, training run as a local process
make terraform-test   # needs Terraform >= 1.7
```
